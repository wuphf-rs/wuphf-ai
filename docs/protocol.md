# Connector Protocol

## Purpose And Transport

The first `wuphf` protocol is a gRPC-facing behavioral contract between the
Rust core and a connector instance. Each connected connector instance opens one
long-lived bidirectional stream. This stream carries registration, normalized
incoming events, durable dispatch commands, and dispatch outcomes.

The protocol supports create-message replication only. The canonical
definition and compatibility-managed field assignments are in
[`../proto/connector.proto`](../proto/connector.proto); Rust bindings are
generated by the `wuphf-proto` crate.

## Registration And Authentication

The first connector-to-core operation on a stream is `Register`. It supplies
the connector's configured connector ID and shared token. The core compares
these with configured credentials and replies with a registration response.

Only an accepted connector instance may submit origin events, receive dispatch
commands for its endpoints, or report dispatch outcomes. Shared-token
authentication is the MVP requirement; mTLS and multi-session management are
deferred.

## Connector-To-Core Operations

- **Register**: identifies and authenticates a connector instance when opening
  its stream.
- **Submit `CreateMessage`**: reports a newly observed normalized platform
  message originating from an endpoint controlled by the connector.
- **Acknowledge dispatch**: reports that a dispatch command succeeded and
  supplies the resulting target platform message ID.
- **Report dispatch failure**: reports an unsuccessful dispatch attempt and may
  mark it permanent. Unmarked failures retain retryable behavior for
  compatibility with the initial MVP contract.

## Core-To-Connector Operations

- **Registration response**: accepts or rejects registration and establishes
  whether the stream may be used.
- **Durable `DispatchCreateMessage`**: asks a connector instance to create a
  target platform message from a logical message. Its durable identity enables
  retries and idempotent outcome handling.

## Normalized Create Message

A submitted `CreateMessage` carries:

- Connector event ID, stable for retrying an observation from that connector.
- Origin endpoint.
- Origin platform message ID.
- Sender information.
- Timestamp.
- Text content.
- Optional replied-to platform message ID at the origin endpoint.
- Zero or more attachment descriptors.

An attachment descriptor records metadata for one item and classifies it as one
of:

- `image`
- `video`
- `audio`
- `file`
- `sticker`

Descriptors can carry metadata needed to represent the message, but the MVP does
not transfer, upload, download, or persist blob/media bytes through the core
protocol.

## Delivery Rules

- **Deduplication**: retrying the same connector event ID must not create a
  second logical message or duplicate fan-out. A message copy caused by a
  prior dispatch must not re-enter routing as a new logical message.
- **Durable retry**: the core persists a dispatch command before delivery and
  can retry unfinished work after a connector reconnects or the core restarts.
  During an active session, it records attempt count and waits for the
  acknowledgement timeout or bounded exponential backoff before redelivery.
- **Idempotent acknowledgement**: receiving the same successful acknowledgement
  again must result in the same completed dispatch and message copy.
- **Per-endpoint ordering**: the core sends eligible dispatch commands to each
  target endpoint in order. A permanently failed command blocks subsequent
  commands for that endpoint rather than violating order.
- **Blocked replies**: when a logical message replies to another message, a
  target dispatch remains blocked until the parent message copy has been
  acknowledged at that target endpoint. The dispatched reply then refers to
  that target-side parent platform message ID.

SQLite-backed core state is required to uphold these delivery rules across
process and connection lifetimes.

## Reserved Future Operations

The contract should be evolved deliberately to later represent edits,
reactions, deletes or revokes, and any explicit media transfer mechanism.
Those operations are reserved direction, not functionality in the first MVP.
