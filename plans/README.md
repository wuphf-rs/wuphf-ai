### Runtime settings 034–043 (added 2026-10-25 at `643829b`)

Designed in an interview with the owner. wuphf becomes a host of the
`botconf` settings framework, which moves out of `assistant_bot_rs` into its
own repo, `github.com/propheci/botconf` (Rust crates, a Go SDK and a shared
proto; its own `plans/` hold the framework work). Settled decisions, not to be
reopened by executors:

- The Rust core owns the only settings store. Connectors are front ends: they
  render the settings panel and forward presses and typed values, and the core
  decides who may change what.
- Connectors authenticate with per-connector tokens, and a second session for
  a live connector id is rejected (034). Owner ids per connector are file-only,
  as the root of trust (039).
- Rules become a map keyed by `RuleId` so each rule is its own setting (038).
- Connectors declare their own settings at registration with a JSON Schema;
  the core stores and validates them and pushes changes back through `Watch`.
  Only settings that apply live are runtime keys (040).
- The Telegram connector opens the panel with `/wuphf` (configurable). It is
  caught before the `message.Out` drop and never mirrored. User sessions show
  the panel through a helper bot (a second gotd client in the connector) using
  the inline-bot trick (041). User-session stickers then go through the same
  helper bot, falling back to the bold label plus a reply (043).

Dependencies and ordering:

- **034 is independent** and can land first. 039 needs it, since settings
  arrive over connector sessions.

## Findings considered and rejected

(Recorded so nobody re-audits them.)

- **Acknowledgement assignment race in the connector hub** (reported by audit
  subagent): not a race — `ConnectorHub::accept_input` mutates via `&mut self`
  in a single task; the owner check-then-remove
  (`crates/wuphf-runtime/src/connector.rs:177-191`) is atomic within the hub.
  By design.
- **Instagram drops media on CDN failure and bridges text-only**: deliberate,
  documented trade-off (`connectors/instagram/internal/instagram/updates.go:125-127`)
  — a bad CDN URL must not tear down the session. Optional UX marker not worth
  a plan now.
- **Missing send timeout around Instagram `WaitUntilCanSendMessages`**:
  speculative; the caller's context carries cancellation. No observed hang.
- **Session-cookie file permissions**: Instagram already writes `0o600`
  (`connectors/instagram/internal/instagram/connector.go:129`); remaining risk
  is operator umask, a docs concern at most.
- **Media-prune clock skew (`SystemTime` in `now_ms`)**: a backwards clock
  only delays orphan pruning; bounded, self-correcting, not worth code.
- **Root `.env.example`**: connector env vars are already documented in each
  `config.example.toml`'s comments; a central file would duplicate them.
- **`format!`-built SQL as an injection vuln**: all call sites pass literals —
  not exploitable; downgraded to the hardening item in plan 010.
- **"Router crate has zero tests" as stated**: technically true at crate
  level, but `wuphf-core/src/tests.rs` (17 tests) exercises most routing
  behavior end-to-end. The real gaps — delete replication (zero coverage
  anywhere) and router error branches — became plan 007.

From the 2026-07-07 architecture audit:

- **Dead `CoreError::UnsupportedEvent` variant** (`wuphf-core/src/lib.rs:196`,
  never constructed since reactions landed): delete opportunistically in any
  plan touching that file; not worth its own plan.
- **TUI platform abbreviations (`wuphf-tui/src/ui.rs:257`) as "duplication"**:
  presentation-layer mapping over the *proto* enum, distinct concern from the
  model-side mapping consolidated by plan 022. By design.
- **Hoisting dispatch settlement out of storage into the core**: rejected —
  SQLite settles inside one transaction; splitting across trait calls loses
  crash-atomicity and would strand blocked dispatches on a mid-settlement
  crash. Plan 019 single-sources the *decisions* in `shared.rs` instead.
- **grpc.rs proto mapping verbosity** (`wuphf-runtime/src/grpc.rs`): inherent
  wire-boundary code; splitting or macro-izing it would hide the contract.

From the 2026-10-21 simplification batch:

- **Session hub "mirrors the dispatch queue"** (`ConnectorHub.assigned` and
  `.held` in `crates/wuphf-runtime/src/connector.rs`): looked like a duplicate
  of storage's pending queue, but it is per-session delivery tracking, which
  storage cannot provide. Replacing it with "ask storage for pending work on
  reconnect" races the shared dispatch channel: a dispatch that is both
  pending in storage and still queued in the channel would be sent twice, and
  one acknowledged between the storage read and the channel delivery would be
  resent. Avoiding that needs per-session tracking again. Not worth doing.
- **Folding `participant` into `author_id`**: on WhatsApp `participant` always
  equals the author today, but WhatsApp's sender uses it to address quoted
  replies. Needs its own check across all three connectors; left out of 027.
- **Converting every connector-plus-chat field pair to `ChatRef`**
  (`OwnerMessage`, `Alias`, `AddressLink`, `ObservedMessage`,
  `SourceAddress`): wide churn for little clarity; 028 introduces `ChatRef`
  for notice targets and 031 for a conversation's source only.

From the 2026-10-22 remote-functions design:

- **A typed media-conversion service instead of a general registry**: the
  owner chose a general registry so later helpers need no core change.
- **Directory mode (the core returns a provider address; callers dial it)**:
  needs every provider to listen and be reachable, duplicates auth and
  timeouts in each client, and hides calls from the core.
- **Load-balancing several providers of one function**: rejected for v1 in
  favor of a single owner with same-id takeover; revisit if one converter is
  not enough.
- **The core converting media while planning a dispatch**: dispatch planning
  is synchronous and deterministic; a remote call there needs a new dispatch
  state and couples correctness to provider uptime. Spike first if wanted.
